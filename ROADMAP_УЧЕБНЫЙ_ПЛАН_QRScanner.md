## 0. Как пользоваться этим документом

1. **Не читайте документ целиком «на будущее».** Открывайте только тот этап, который делаете сейчас.
2. Идите **строго по шагам**: `A1 → A2 → ...`. Не перескакивайте: каждый следующий шаг опирается на предыдущий.
3. Внутри шага: прочитать → сделать → проверить → закоммитить → записать в журнал.
4. **Критерий готовности** — это не «вроде работает», а конкретная проверка, которую можно повторить. Если проверка не проходит — шаг не закрыт.
5. Отмечайте `[x]` только после проверки. Отметка без проверки — самообман.
6. Если шаг занимает больше 3 сессий — вы взяли слишком крупный шаг, разбейте его сами и запишите, как разбили.

## 2. Две полосы: полигон и тренажёр

Одна из главных ошибок новичка — пытаться «дописать проект» и «научиться писать» в одном и том же файле. Это разные навыки, и они мешают друг другу. Поэтому работаем в двух папках.

### 2.1. Структура папок

```
F:\CURSOR\
├── QRScanner1\            ← ПОЛИГОН (уже есть). Чиним, доводим, не переписываем.
└── QRScannerLearning\     ← ТРЕНАЖЁР (создадите в шаге A5). Пишем сами с нуля.
```

Журнал и вспомогательные файлы — **вне обоих репозиториев**, чтобы не мешать коду:

```
F:\CURSOR\УЧЕБА\
├── ЖУРНАЛ.md              ← главный документ курса (создадите в шаге A6)
├── json-тесты\            ← 4 файла для модуля 10
└── скриншоты\             ← для портфолио
```

### 2.2. Правила полос

| | Полигон (`QRScanner1`) | Тренажёр (`QRScannerLearning`) |
|---|---|---|
| Цель | довести чужой код до рабочего сценария | научиться писать самому |
| Что делаем | читаем, находим причину, минимально правим | пишем с нуля, можно «плохо, но работает» |
| Что нельзя | переписывать всё, тащить новые фичи, копировать свои учебные решения целиком | копировать код полигона вместе с его багами |
| Язык | Java + XML (как есть) | Java + XML до шага `E3`, дальше — Kotlin/Compose по желанию |
| Ветка/репо | `fix/roadmap` | свой `git init` |
| Коммит | `fix: ... (P0-X)` | `feat: ...` / `learn: ...` |

### 2.3. Чередование полос

**Одна неделя — одна полоса.** Не делите одну сессию между полигоном и тренажёром: переключение контекста съедает больше времени, чем экономит.

Порядок всегда такой: **сначала сделал сам в тренажёре → потом идёшь чинить похожее в полигоне.** Тогда в полигоне вы узнаёте знакомую боль, а не применяете инструкцию.

## 5. Рабочий цикл одного шага

Каждый шаг делается по одному и тому же шаблону. Записывайте это в журнал, тогда прогресс будет виден.

```
1. ПРОЧИТАТЬ   — раздел учебного плана, указанный в шаге (20–40 мин)
2. СДЕЛАТЬ     — по пунктам шага, не отвлекаясь на «а ещё можно...»
3. ПРОВЕРИТЬ   — прогнать проверку из шага на устройстве/эмуляторе
4. ЗАКОММИТИТЬ — git add <конкретные файлы> && git commit -m "<тип>: <что>"
5. ЗАПИСАТЬ    — 5 строк в ЖУРНАЛ.md
```

**Правило 40 минут:** если застряли — 15 минут сами, 15 минут на второй подход с другой гипотезой, ещё 10 минут на гугл/документацию. Если не вышло — **отложите шаг до следующей сессии**, запишите гипотезу и текст ошибки в журнал. Сидеть 3 часа над одной ошибкой новичку вредно: падает мотивация, а не растёт навык.

**Правило коммита:** один коммит = один смысл. Не смешивайте «починил баг» с «переименовал файлы».

**Правило проверки:** проверяем **на устройстве**, а не «в голове». Эмулятор подходит, но камеру на нём надо настроить (см. раздел 10).

### A2. Зафиксировать git и wrapper

**Полоса:** полигон · **Время:** 0,5–1 ч · **Модуль:** 0 (↔ P3-6)

**Зачем:** сейчас в рабочей папке лежат незакоммиченные изменения. Пока они не зафиксированы, любой следующий шаг смешается с ними, и вы не сможете откатиться.

**Делать:**

1. Посмотреть, что происходит:
   ```powershell
   git status --short
   git diff --stat
   ```
   Ожидаемо: 680 удалений `app/build/...`, изменения в `build.gradle` и `gradle/wrapper/gradle-wrapper.properties`, новые `gradlew.bat` и `gradle/wrapper/gradle-wrapper.jar`.
2. **Не делайте `git add -A`** — иначе в коммит попадут учебные документы, картинки и ТЗ. Добавляйте только нужное:
   ```powershell
   git add .gitignore
   git add gradlew.bat
   git add gradle/wrapper/gradle-wrapper.jar
   git add gradle/wrapper/gradle-wrapper.properties
   git add build.gradle
   ```
   Удаления `app/build` уже в индексе — трогать не нужно.
3. Проверить, что в коммит не попадёт лишнее:
   ```powershell
   git status --short
   ```
   В `Changes to be committed` не должно быть `app/build/...` (кроме уже удалённых), `local.properties`, `*.apk`.
4. Сделать коммит:
   ```powershell
   git commit -m "chore: Gradle Wrapper 8.6, AGP 8.4.0, артефакты сборки вне git"
   ```
5. Проверить результат:
   ```powershell
   git ls-files app/build
   ```
   Команда должна **ничего не вывести**.
6. Отдельным коммитом (по желанию, но полезно) зафиксировать документы:
   ```powershell
   git add PROJECT_ROADMAP.md ROADMAP_*.md УЧЕБНЫЙ_ПЛАН_*.md CLASS_DEPENDENCIES.md
   git commit -m "docs: roadmap и учебные планы"
   ```

**Проверка:**

- [ ] `git ls-files app/build` — пусто.
- [ ] `git log --oneline -3` показывает ваши коммиты.
- [ ] `git status` чистый, кроме осознанно не добавленных файлов.
- [ ] `gradle\wrapper\gradle-wrapper.jar` есть в git: `git ls-files gradle/wrapper`.

**Если не работает:**

| Симптом | Причина | Решение |
|---|---|---|
| `gradle-wrapper.jar` не добавляется | `.gitignore` содержит `*.jar` | Убрать строку или `git add -f` |
| `nothing to commit` | изменения уже закоммичены ранее | Проверить `git log`, идти дальше |
| Git ругается на `app/build` | индекс не обновлён | `git rm -r --cached app/build` повторить |

   ```powershell

   ```

   ```powershell
   adb devices
   ```

   ```powershell
   adb install -r app\build\outputs\apk\debug\app-debug.apk
   ```
6. Запустить и посмотреть логи:
   ```powershell
   adb logcat -c
   adb logcat -s ScanActivity:D DebugLogger:D
   ```

## 14. Типовые ошибки и что делать

### 14.1. Сборка

| Симптом | Причина | Решение |
|---|---|---|
| `Unsupported class file major version` | Не тот JDK | `Settings → Build → Gradle → Gradle JDK = 17` |
| `SDK location not found` | Нет `local.properties` | Открыть проект в Android Studio один раз |
| `Could not resolve ...` | Нет сети / не тот репозиторий | `Sync`, проверить `google()` и `mavenCentral()` |
| Долгий первый Sync | Скачивание Gradle и зависимостей | Это нормально, ждать 5–15 минут |
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | Установлена сборка с другой подписью | `adb uninstall com.example.qrscannerlearning` |
| Изменения не видны на устройстве | Установился старый APK | `Build → Clean Project`, затем `assembleDebug` заново |

### 14.2. Камера

| Симптом | Причина | Решение |
|---|---|---|
| Чёрный экран, «Camera already in use» | `resume()` вызван дважды | Флаг `scanningActive` (шаг C2/C3) |
| Камера не работает после возврата | Не вызван `resume()` в `onResume` | Парность `pause()`/`resume()` |
| На эмуляторе нет изображения | Камера не настроена | `Extended controls (⋯) → Camera → Emulated/Webcam0 → Virtual scene` |
| Скан не срабатывает | Код слишком мелкий/блики | Приблизить, включить свет, подержать 2–3 секунды |

### 14.3. Данные и потоки

| Симптом | Причина | Решение |
|---|---|---|
| `Cannot access database on the main thread` | Запрос в UI-потоке | `Executor` / `LiveData` из Room |
| Список пуст после скана | Разные экземпляры репозитория | Singleton (шаг D2/D3) |
| Данные пропали после перезапуска | `fallbackToDestructiveMigration` / пересоздание БД | Проверить версию БД и миграции |
| Приложение «замирает» на экспорте | Работа в UI-потоке | Фон + `Handler`/`LiveData` (шаг F5) |

### 14.4. Файлы

| Симптом | Причина | Решение |
|---|---|---|
| `FileUriExposedException` | Передача `file://` | `FileProvider` (шаг F3) |
| Excel показывает кракозябры | Нет BOM / не UTF-8 | UTF-8 + BOM для CSV |
| Файл не открывается у получателя | Не дан `FLAG_GRANT_READ_URI_PERMISSION` | Добавить флаг |
| «Файл не является JSON-массивом» | Корень — объект | Поддержать `{items:[...]}` (шаг F1) |

### 14.5. Процесс

| Симптом | Что делать |
|---|---|
| Застрял больше 40 минут | Записать гипотезу и ошибку в журнал, отложить до следующей сессии |
| Пропущена неделя | Вернуться к тому же шагу, **не** начинать следующий |
| «Всё сломалось» | `git diff`, затем `git stash` или `git checkout -- <файл>`, вернуться к последнему зелёному коммиту |
| Скучно | Проверить, не застряли ли на теории: должно быть 70% практики |
| Хочется переписать всё | Записать в журнал и отложить до этапа G; сейчас курс, а не продукт |

## 16. Если выпали из графика

Это случится. План на 30 недель не выполняется идеально, и это не провал.

1. **Не начинайте новый шаг**, пока не закрыт текущий. Лучше отстать на 2 недели, чем потерять нить.
2. **Вернитесь к последней записи в журнале** — там написано, что делать дальше. Не надо вспоминать.
3. Если перерыв был больше месяца:
   - пересоберите проект (`assembleDebug`);
   - прогоните сценарий текущего шага;
   - если не помните, как это работает — перечитайте только этот раздел плана, не весь план.
4. Если мотивация упала:
   - сделайте **маленький** шаг на 30–40 минут (например, `B1`, упражнение с цветом кнопок);
   - покажите кому-нибудь работающий экран;
   - запишите в журнал, что уже умеете — список будет длиннее, чем кажется.
5. **Не меняйте маршрут на середине.** Если хочется бросить Java и уйти в Kotlin — запишите это в журнал и вернитесь к вопросу после шага `D3`. Скорее всего, к тому моменту желание пройдёт, потому что появится работающий сценарий.

## 19. После курса: современный стек

Когда маршрут пройден (или хотя бы этап D), переходите на Kotlin + Compose. Это не «ещё один курс», а смена инструмента при том же понимании Android.

**Порядок:**

1. **Kotlin** — 2–3 недели: синтаксис, null-safety, `data class`, extension functions, лямбды.
2. **Coroutines/Flow** — вместо `Executor` и `LiveData`.
3. **Jetpack Compose** — декларативный UI вместо XML.
4. **Hilt** — вместо ручных синглтонов.
5. **Retrofit/OkHttp** — сеть.
6. **WorkManager**, **Paging 3** — по необходимости.
7. **Play Console** — публикация.

**Практика перехода (конкретно):** создайте третий проект `F:\CURSOR\QRScannerCompose`, в нём один экран «Список кодов» на Kotlin + Compose с теми же данными (Room остаётся тем же). Сравните объём кода с XML-версией и запишите в журнал.

**Почему так:** Java + XML — фундамент и legacy-поддержка. Kotlin + Compose — то, на чём пишут новые приложения и то, что спрашивают на собеседованиях. Первое даёт понимание, второе — скорость и актуальность.
